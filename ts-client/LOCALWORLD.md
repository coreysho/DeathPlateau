# A local world to test clients against

The live server is not a test rig. Logging a client into it means creating accounts on a
production database and putting characters in the world other people are playing in. This sets up
a complete world in a container instead, which costs about five minutes and then costs nothing.

Everything below was run on 2026-11-16 and the world came up: `World ready`, 12,669 static NPCs,
and the ts377 client authenticating against it with login response 2.

## Setup

    git clone --depth 1 -b 377-wip https://github.com/coreysho/deathplateau-content ../content
    cd <engine>
    npm install
    npx tsx tools/server/rsa.ts        # prints the modulus - keep it, the client needs it
    npm run sqlite:migrate
    npm run build                      # packs the cache from ../content, ~25s
    npx tsx src/app.ts

`.env` needs only this:

    DB_BACKEND=sqlite
    WEB_PORT=8888
    NODE_PORT=43594
    NODE_PROFILE=main
    LOGIN_SERVER=false

The engine finds content at `../content` (`BUILD_SRC_DIR`), so the clone has to be a sibling of
the engine directory.

**Unknown usernames are registered on first login** (`LoginThread.ts`), so no account setup is
needed - any name works, and the accounts only exist in the container's sqlite file.

## Pointing a client at it

Two things differ from the live server, and both bit before they were understood.

**The login keypair.** `tools/server/rsa.ts` generates a fresh one, so a client with the live
server's modulus baked in gets its login block rejected - and the engine answers that with
response **6**, "RuneScape has been updated! Please reload this page", because it sends "out of
date" on an RSA failure deliberately. A revision error looks exactly the same from the client, so
the message is worth distrusting: `World.ts` sends 6 from three different places.

`ts377-rsa-override.patch` makes the client read `__RSA_MODULUS` off the page instead, and
`entry.ts` takes it from `?rsa=<modulus>`. It has to be a getter, not a field: a static field
initialises when its module is imported, which happens before `entry.ts` runs, so a field reads
the override before anything has set it.

**The revision.** The engine takes `ENGINE_REVISION` (384) or `LOGIN_LEGACY_REVISION` (381). The
ts377 client announces 381, so it passes as-is. `ENGINE_REVISION=377` in `.env` is the documented
escape hatch if a client needs it.

## The rig

`rig/serve.js` serves the built bundle at `/ts/` and forwards everything else to a world - the
cache routes over HTTP and, importantly, the game WebSocket through an upgrade proxy, because the
client builds its socket URL from the page's own origin.

    node serve.js <dist-dir> 127.0.0.1:8888      # the local world
    node serve.js <dist-dir> play.deathplateau.com

## Where this got to

The ts377 client reaches the game world. Logged in, `loadingStage` 2, scene drawn, **50 fps held
for 40 seconds with 2 failed frames**, both at startup.

50 is the ceiling, not a score. `GameShell` computes `fps = 1000 * ratio / (deltime * 256)`, and
with `ratio` capped at 256 and `deltime` 20 that tops out at exactly 50 - so the client is running
flat out. It is also a desktop-class container CPU drawing a near-static new-character screen, so
**this is still not the Phase 0 gate number**. What it is, is the first time the game loop has run
in the world at all.

`ts377-ingame.patch` holds what it took, and all four pieces are the same kind of defect: the
machine translation dropped something the Java original does deliberately.

**Per-frame fault handling** (`GameShell.ts`). The Java client wraps `update()` and `draw()` in
`catch (Throwable)` each and only clears its fault counter on a frame that got through both -
`boolean clean = true` in `GameShell.java`. The port dropped that, so the first exception escaped
the async loop and the client stopped dead: no more logic, no packets, no frames. That is what
made a one-frame error look like a hang, and it masked every bug behind it.

**Null-children guards** (`Game.ts`, four sites). `children` is only allocated for container
widgets - `com.children = new int[childCount]` sits inside the type-0 branch of `Component.java` -
so a non-container interface has none. The Java client folds the check into its early returns,
`arg.type != 0 || arg.children == null || ...`. The port kept the type test and dropped the null
test, so opening a childless interface threw.

**Unknown opcodes are skipped, not fatal** (`Game.ts`). The original logs out when it meets an
opcode it does not know, on the assumption that the stream has desynced. Against this server that
assumption is wrong: DeathPlateau adds nine packets no stock 377 client has seen. Each is now
reported once, so what still needs a handler stays visible.

**The nine custom packet sizes** (`PacketConstants.ts`, generated by `tools/gen-ts377-sizes.mjs`).
This is the one that actually mattered, and it is worth being precise about why, because skipping
without it made things worse rather than better:

    PING 3 · IF_SETINVWINDOW 6 · IF_SETINVBREAKS 18 · IF_SETINVOP -1 · P_DIALOGPROMPT -1
    MESSAGE_CLAN -1 · UPDATE_CLANCHANNEL -2 · SET_LOGIN_TOKEN -1 · VARP_BATCH -2

A stock client has 0 for all nine. 0 does not mean "empty" - it means read no length and no
payload, so the next payload byte is read as an opcode and the stream is lost from there. With
`logout()` on an unknown opcode that desync ends the session immediately, which is at least loud.
Skipping without fixing the sizes turned it into a cascade of invented opcodes that hung the
client outright. The sizes are what make skipping safe.

## Still open

- `localPlayer` stays null and the screen shows the new-character design interface, because every
  account the rig creates is new. Completing the design, or logging in an existing character, is
  the next step toward a populated-world measurement.
- `PING` (opcode 1) is received and skipped, so nothing answers it. The engine wants `PONG`
  (client opcode 2, size 1) and times the session out after 60s without it.
- Two frames still fail at startup on a null buffer: `loggedIn` is set the moment the server
  replies 2, but `method122()` builds the game-screen buffers several awaits later. Harmless now
  that a faulty frame is survivable, but it is a real race and the fix wants the login-to-game
  handover read as a state machine.
